Публикация в GHCR разрешена только из main после успешных проверок; путь
образа приводится к нижнему регистру, тег соответствует SHA коммита.

Создан активный ruleset «Защита main»: PR и одно одобрение обязательны,
force push и удаление запрещены, обходов нет. Сейчас обязательны три проверки
исходного CI: «Стиль кода», «Тесты», «Сборка образов». После внесения нового CI
необходимо также сделать обязательными «Проверка связки» и «Поиск паролей».
Публикацию требовать на PR нельзя: на нём она намеренно пропускается.

## ПЗ 4. Контейнеры и сетевое взаимодействие

Dockerfile заказов использует два этапа и Python slim, пользователь — `app`.
Зависимости устанавливаются до копирования исходников. После изменения только
исходника слой pip повторно использован из кеша. В контекст не входят тесты,
локальные базы, .env и кеши.

Измерения на одном компьютере, несжатый размер образов Podman:

| Образ | Размер, байт | Размер, МБ |
| --- | ---: | ---: |
| Исходный из начального коммита | 1 201 603 734 | 1 201,60 |
| Многостадийный с SQLAlchemy и Alembic | 221 042 264 | 221,04 |

Снижение примерно в 5,4 раза; новый образ дополнительно содержит зависимости
для хранения заказов. Последующее исправление HTTP-клиента слегка меняет размер.

Compose проверен также в настоящем Docker 29.3.0 без прав администратора:
PostgreSQL и оба сервиса достигли healthy. Созданы клиент и его заказ,
проверены чтение и фильтрация. `whoami` в заказах возвращает `app`.
После остановки клиентов получен 503 за 2,019 секунды. Общий предел времени
реализован через асинхронный HTTP-клиент и asyncio.timeout, поэтому включает
поиск сетевого имени. Данные обоих сервисов находятся в PostgreSQL;
версия миграций заказов хранится отдельно от версии миграций клиентов.

## ПЗ 5. Стенд OpenTofu

OpenTofu 1.10.6, Docker-провайдер 3.9.0. Конфигурация проходит fmt и validate.
План для двух серверов: 7 ресурсов — сеть, том, два образа, база, два сервера.
Создание всех семи ресурсов выполнено; SSH-вход под deploy проверен.
В конфигурации исправлено раскрытие ~ в пути к открытому ключу, добавлены
проверка числа серверов и готовый вывод inventory. Lock-файл провайдера
сохраняется в Git, состояние и локальные параметры игнорируются.

При использовании совместимого API Podman повторный план предложил
пересоздания из-за отличий от Docker. Для итоговой проверки использован
отдельный Docker в режиме rootless. Повторный план подтвердил отсутствие изменений; затем удалены все семь ресурсов,
вновь созданы все семь, имена и порты совпали. Результаты
удаления и восстановления записаны в `docs/evidence/stand.txt`.

Совместный опыт с двух компьютеров пока не выполнен. С локальным состоянием
и локальным Docker каждый участник создаёт собственный стенд с другими IDs.
Два разных состояния на одном Docker конфликтуют именами; блокировка одного
локального файла не координирует два независимых состояния. Это объяснение
не заменяет фактическую проверку обоими участниками.
