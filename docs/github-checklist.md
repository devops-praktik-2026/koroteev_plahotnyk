# GitHub и совместные проверки

Этот список закрывается по фактическим ссылкам и результатам. Локальные
коммиты и проходящие тесты не подтверждают ревью, защиту ветки или работу доски.

## ПЗ 1

- Заполнить состав пары в README: имена, GitHub-ники, роли.
- Убедиться, что оба участника имеют право записи.
- Создать GitHub Project с колонками «Список задач», «Готово к работе»,
  «В работе», «На проверке», «Готово».
- Создать issues из docs/tasks. Этап 1 перенести в «Готово к работе»,
  остальные оставить в списке. В работе максимум одна задача на человека;
  на проверке максимум одна на пару.
- Включить автоматическое перемещение закрытых issues в «Готово».
- Создать отдельную карточку состава пары; ветка, изменение README,
  PR с `Closes #<реальный номер>`, содержательный комментарий напарника,
  слияние напарником. Сохранить ссылки и скриншот перемещения карточки.
- Согласовать критерии готовности через PR.

## ПЗ 2

Локальная ветка подготовки: `codex/devops-practicals`. Её материалы нужно
разнести по карточкам и PR по правилам курса; сама она не заменяет эту работу.
Коммит `da5cf3d` содержит тесты API до реализации `7479ed8`.
Коммит `1eebbcf` содержит тесты проверки клиента до реализации `f6dffdb`.

- Описание поведения: карточка 1.1, docs/orders-api.md, отдельный PR.
- Создание заказа: карточка 1.2; проверить порядок «тест → код» в истории.
- Получение заказа: карточка 1.3.
- Список заказов: карточка 1.4. Разделить 1.3 и 1.4 между участниками.
- Каждый PR проверяет и сливает напарник; автор не одобряет собственный PR.

## ПЗ 3

- Отправить изменения CI через PR, дождаться реальных запусков GitHub Actions.
- Проверки: «Стиль кода», «Тесты», «Сборка образов», «Проверка связки»,
  «Поиск паролей». Порог покрытия сейчас 80%; подтвердить договорённость пары.
- «Публикация образа» выполняется только после успешных проверок при push
  в main. Её не включать в обязательные проверки PR: на PR она пропускается,
  и требование такой проверки могло бы заблокировать внесение изменений.
- После слияния проверить Packages: нижний регистр пути, тег SHA коммита.
- Создать активный ruleset «Защита main» для основной ветки: PR обязателен,
  одно одобрение, проверки выше обязательны, запрет force push и удаления,
  пустой bypass list. Потребуются права администратора репозитория.
- В одноразовой проверочной ветке проверить блокировку плохого стиля.
- На PR без одобрения убедиться, что слияние недоступно.
- Проверить отказ прямой записи в main на отдельной локальной копии.
  Не выполнять `reset --hard` в рабочей копии с несохранёнными изменениями.
- Приложить сообщения GitHub, ссылки и скриншоты в отчёт.

Проверку синтетического секрета безопасно повторить в одноразовом локальном
репозитории: `python scripts/check_secret_scanner.py /полный/путь/gitleaks`.
Это проверяет сканер, но не заменяет демонстрацию красного запуска Actions
на учебной ветке. Настоящие секреты для демонстрации не нужны.

## ПЗ 4

- Проверить `make up`, `make ps`, `make smoke`, отказ соседа и восстановление.
- Сравнить размеры старого и нового образов на одном компьютере.
- Проверить `docker compose exec orders whoami`: ожидается `app`.
- Проверить кеш: при изменении только исходника слой установки зависимостей
  остаётся закешированным.
- Сохранить вывод CI и ссылки на PR карточек 1.5, 2.1–2.4.

## ПЗ 5

- `tofu plan`: 7 ресурсов для двух серверов. `apply`, `state list`,
  `output servers`; повторный apply без изменений.
- `destroy`, повторный `apply`: сравнить имена и порты, проверить новые IDs.
- Оба участника применяют конфигурацию у себя, сравнивают локальное состояние.
  Не передавать файлы состояния в публичный PR: в них может быть пароль БД.
- В описании PR записать реальные результаты совместного опыта.
