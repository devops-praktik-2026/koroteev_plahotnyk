# Поиск секретов — часть карточки 1.6

В `.github/workflows/ci.yml` добавлено задание «Поиск паролей».
Оно запускается на каждом pull request и после отправки изменений в `main`.
Проверки стиля и тестов уже существуют; минимальное покрытие 80% задано
в `pytest.ini` через `--cov-fail-under=80`.

Используется Gitleaks 8.21.2 со стандартными правилами. Архив скачивается
из официального релиза, перед распаковкой проверяется его SHA-256 по файлу
контрольных сумм релиза. `fetch-depth: 0` загружает полную историю Git.
Команда `gitleaks git . --redact --no-banner` проверяет историю, включая
коммиты, в которых файл с секретом уже удалён. Обнаружение секрета даёт
ненулевой код завершения и красную проверку. `--redact` скрывает значения
найденных секретов в выводе.

## Демонстрация

После установки Gitleaks выполнить из корня проекта:

```bash
gitleaks git . --redact --no-banner
python3 scripts/check_secret_scanner.py "$(command -v gitleaks)"
```

Скрипт создаёт отдельный временный Git-репозиторий и проверяет четыре случая:

1. Чистая история — код 0.
2. Коммит с учебным паролем — код 1.
3. Файл удалён следующим коммитом, но пароль остался в истории — код 1.
4. Учебные коммиты убраны из проверяемой истории — код 0.

Случайная строка не используется ни в одном сервисе. Временный репозиторий
удаляется после проверки. История основного проекта не меняется.
Та же демонстрация выполняется в CI: скрипт завершается успешно только
при получении всех ожидаемых кодов. Поэтому ожидаемое обнаружение
учебного пароля не делает весь запуск Actions красным.

Публикация Docker-образа выполняется напарником отдельно. После добавления
публикации её задание должно зависеть в том числе от `secrets-scan`.
Обязательность новой проверки для слияния настраивается отдельно
в правилах защиты `main` в рамках карточки 1.7.
